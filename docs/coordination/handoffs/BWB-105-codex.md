# Handoff: independent review of BWB-105 (stale translation detection and source revisions)

READ-ONLY, offline. Branch `feat/105-stale-translation-detection`. Read: `docs/architecture/TRANSLATIONS.md` (section "Stale translations"), `docs/architecture/COMMANDS.md`, ADR 0003 and 0004 (sourceHash, statuses, LocaleSnapshot/sourceContentRevision), PRD addendum FR-052 to FR-057, code: `packages/core/src/translation/source.ts`, `packages/core/src/json/sha256.ts` (moved from style-engine, new UTF-8 form), `packages/core/src/commands/{apply,schema,types}.ts` (setTranslation, restoreTranslation, restoreStatuses, markStale, applyStatuses, sourceOf), tests `stale.test.ts`, `source.test.ts`, `sha256.test.ts`, `packages/core/corpus/source-digest.json`, `packages/element-registry/src/registry.ts` (`sourceProperties`) and its test, `tests/fixtures/contracts.json` (new suite), `tests/fixtures/src/contracts.ts` (roadmap ids now include the addendum).

Questions:
1. Is the marker sound? 16 hex of SHA-256 over canonical JSON of the default-locale values of the translatable ("source") properties. Collisions are irrelevant for change detection, but check: property-id subset and ordering, absent versus empty values, locale-specific values excluded, what happens when the registry adds or removes a translatable property later (does every translation become stale or silently not stale?), unknown types (hook returns nothing), a default entry with no counted values, NFC/Unicode handling, JSON numbers, and the PHP reproduction rules (UTF-8, canonical JSON escaping): can the corpus and the description alone produce byte-identical results?
2. Flagging rule: default-locale `set-translation` marks draft/translated/reviewed entries whose marker is missing or different when the digest of that element changed. Edge cases: several default edits in a row, edits that revert to the previous text (entries stay stale), entries made from a newer text than the default (marker differs but source did not change in this command), `remove`/`restore` interplay, entries for locales not in `locales`, an element with a default entry created later. Is "missing marker counts as potentially stale" right? Is anything flagged that should not be, or missed?
3. Confirmation flow: a non-default `set-translation` (even status-only) refreshes the marker, so choosing translated/reviewed on a stale entry confirms it. Is that safe (a reviewer can mark reviewed without a text change) and consistent with FR-053? Should `draft`/`reviewed` on an entry leave the marker alone in some cases?
4. Undo/redo exactness: `restore-translation` carries `statuses`, `mark-stale` inverse `restore-statuses`; `applyStatuses` validation (live entries only, orphaned refused, duplicates). Could an inverse fail or be abused? Command size limits (`restore-statuses` up to 5000x64 records), time complexity of `mark-stale` on 5000 elements x 64 locales, memory.
5. Hash module move: `sha256Hex` (ASCII-only, throws otherwise; relied on by the compiler's `invalid-identifier` handling) and new `sha256HexUtf8`: correctness for lone surrogates, boundary lengths, and PHP equivalence. Dependency direction (style-engine now imports core's hash).
6. Docs/tests: accuracy of TRANSLATIONS.md and COMMANDS.md; which mutations would still pass (digest subset, status set MARKABLE, marker refresh, dropStream, locale checks)? Is the seeded invariant test strong enough? The contracts check now reads the addendum roadmap too: any issue with that?

Output: Blocker/Major/Minor with file + fix wording; agreements; what you could not verify.
