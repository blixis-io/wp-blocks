# Handoff: independent review of BWB-021 (element registry)

READ-ONLY, offline. Branch `feat/21-element-registry`. Read: `docs/architecture/EXTENSION-API.md`, `packages/element-registry/src/*.ts` (definition, registry, checks, core-elements, url) and tests, `packages/element-registry/manifest/core-elements.json`, ADR 0003 (translatable vs invariant), ADR 0009 (namespaces, fallback classes), `docs/product/PRD-ADDENDUM-MULTILINGUAL-THEMES.md` (FR-051, FR-056), `packages/core/src/commands/apply.ts` (canNest hook).

Questions:
1. Registration security and integrity: can a vendor impersonate a core or paid namespace (e.g. `blixis-plus` vs `blixis_plus`, Unicode lookalikes, `Blixis/`, trailing dots)? Can a definition escape validation (prototype-named props, `__proto__` keys through JSON, huge `allowedParents`, regex DoS in `NESTING_ENTRY`)? Is freezing/cloning sound (structuredClone of non-plain input, getters)? Does `register` ever throw or leave a half-registered state?
2. `isSafeUrl`: bypasses for dangerous schemes or markup injection (control characters, Unicode spaces, mixed case, `&Tab;`-style references without semicolon, percent/double encoding, IDN/punycode, `//` after leading characters, `/..;/`, `\\`-equivalents, `data` in relative position, `mailto:` header injection with `?cc=` and newlines, `tel:` oddities, very long inputs, RTL overrides). Is the "relative reference with a colon" rule right (e.g. `a/b:c` allowed?)? Does the reference-decoding concern (`&colon;` without trailing `;`, `&#58` without semicolon) matter?
3. canNest semantics: asymmetric rules, `#root`, categories, unknown types, parents that allow a category but whose child lists parents by type, add-on registered after documents exist, interaction with the commands hook (insert/move/restore), cycles in nesting rules. Is "unknown parent -> false" right for existing documents that contain unknown types (editing children of an unknown parent)?
4. Classification model vs ADR 0003: translatable only strings; locale-specific string/url/media; `required` only meaningful for invariant (translatable required?). Is `checkAgainstRegistry` complete: translation values for locale-specific props in the default locale, entries whose element exists but locale unknown, status `orphaned` for existing element, unknown types skipping, duplicate prop kinds; `message.includes(...)` string matching to derive issue codes (fragile?).
5. Manifest: is it sufficient for PHP (renderers, REST) and stable (canonical ordering, versioning)? Anything executable or environment-dependent in it?
6. Tests: which behaviour has no failing-case test; would they fail if `canNest` dropped the child-accepts-parent half, if the namespace check were removed, or if `describe`/valueSchemaFor were weakened?

Output: Blocker/Major/Minor with file + fix wording; agreements; what you could not verify.
