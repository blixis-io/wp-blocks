## Blocker

- [VERSIONING-AND-COMPATIBILITY.md:60](docs/architecture/VERSIONING-AND-COMPATIBILITY.md:60) says tightening nesting is safe for stored content. The current registry says otherwise: [checkAgainstRegistry](packages/element-registry/src/checks.ts:54) reports existing, now-illegal nesting as an error. `canNest(..., 'relocate')` only relaxes placement for an *unknown child*; it does not grandfather known types. **Fix:** classify narrowing either `allowedParents` or `allowedChildren` as breaking until validation has an explicit legacy-content rule, with fixtures for load, edit, publish, and render.

- [VERSIONING-AND-COMPATIBILITY.md:60](docs/architecture/VERSIONING-AND-COMPATIBILITY.md:60) also says an unknown type renders with “the fallback class the definition declared.” Once its add-on is absent, the current registry has no definition or fallback class to consult; [checks.ts](packages/element-registry/src/checks.ts:46) only issues a warning. ADR 0009 places the fallback declaration in a future manifest, and `retained` needs a published snapshot. **Fix:** specify where the fallback class and retained output are persisted for an inactive add-on; describe current behavior as pending that implementation.

## Major

- [VERSIONING-AND-COMPATIBILITY.md:38](docs/architecture/VERSIONING-AND-COMPATIBILITY.md:38) silently amends two accepted ADRs. [ADR 0004](docs/architecture/adrs/0004-publication-model-and-revisions.md:56) does **not** include `COMPILER_VERSION` in its cache key, while [ADR 0005’s rollback rule](docs/architecture/adrs/0005-style-resolution-and-css-output.md:84) says output-changing compiler changes bump document `schemaVersion` and retain migration fixtures. A separate compiler version and cache key is a sound approach, but it is a **new decision**, not a restatement. **Fix:** explicitly supersede or amend those ADR clauses; define whether an output-only change needs a document migration and include the breakpoint registry if cache output can vary by it.

- [VERSIONING-AND-COMPATIBILITY.md:51](docs/architecture/VERSIONING-AND-COMPATIBILITY.md:51) has two incompatible interpretations of “two further API versions.” Removal *in* `N+2` leaves a deprecated feature working through `N+1`, not through two further versions. Use “supported through `N+2`, removable in `N+3`,” or state that `N+2` is the second version and removal may occur there. The two-plugin-minor-release condition also needs a precise start and counting rule. These windows are **new policy**, not an ADR rule.

- The same [API support rule](docs/architecture/VERSIONING-AND-COMPATIBILITY.md:49) allows refusal beyond `k+2` even if all intervening bumps were additive. Thus an add-on declaring the recommended lowest `requiresApi = k` can stop loading solely because unrelated features were added. Conversely, a feature introduced long after `k` could be deprecated on its own schedule. **Fix:** define compatibility by feature/contract use or a maximum tested API version, and distinguish “no compatibility guarantee” from “host refuses registration.” Today [registry.ts:60](packages/element-registry/src/registry.ts:60) checks only `requiresApi > host`; it cannot enforce an upper bound, detect deprecated fields for warnings, or report which feature an add-on uses.

- [VERSIONING-AND-COMPATIBILITY.md:57](docs/architecture/VERSIONING-AND-COMPATIBILITY.md:57) requires a definition to read every earlier representation, but stored nodes carry no definition version and add-ons have no migration hook. That is workable only for deliberately self-describing, permanently readable properties. It cannot resolve an old and new meaning of the same property ID. **Fix:** require immutable property semantics; for changed meanings use a new property ID or element type, keep the old reader, and test old published content and translations after an add-on update. Mark default changes as conditional: they can change the rendering of old content whose property is absent.

- [VERSIONING-AND-COMPATIBILITY.md:58](docs/architecture/VERSIONING-AND-COMPATIBILITY.md:58) calls widening parents/children and property ranges compatible without qualification. They preserve old content on upgrade, but newly written content may fail on downgrade—the same reason line 25 classifies loosened document limits as breaking. **Fix:** use one stated compatibility direction throughout. Also classify enum-value changes, requiredness, category changes (category based nesting), tier changes, fallback-class changes, and `type` replacement. A category or tier change can alter registration or nesting without any property change.

- [VERSIONING-AND-COMPATIBILITY.md:20](docs/architecture/VERSIONING-AND-COMPATIBILITY.md:20) applies the document’s “optional field: no bump” rule to token sets, whereas [DESIGN-TOKENS.md:51](docs/architecture/DESIGN-TOKENS.md:51) says a token-set “change of shape” bumps its schema version. **Fix:** reconcile that wording explicitly. The rule for live token *values* is sound and agrees with ADR 0004; token schema changes are a separate matter.

- [VERSIONING-AND-COMPATIBILITY.md:27](docs/architecture/VERSIONING-AND-COMPATIBILITY.md:27) has an incomplete schema-change checklist. It omits checking or updating the generated JSON Schema `$id`, TS/PHP semantic validators and issue-code parity, existing published snapshots and downgrade behavior, the migration chain and unknown-field preservation, REST read/write and renderer behavior, and global-class and translation-stream implications. **Fix:** add these as conditional checks tied to the affected contract; a Zod change alone does not cover them.

## Agreements and gaps

Loosened limits as breaking **for downgrade compatibility**, CSS allow-list removal as a breaking visual change, and live token-value edits as cache-invalidating rather than schema-version events are sound. The document should say which downgrade promise it intends to make; it currently applies that standard inconsistently.

The document barely covers translation property changes despite ADR 0003/0004’s separate locale streams and snapshots; it also omits global-class versioning and by-value layout snapshots, REST `blixis/v1` compatibility, and the theme’s `theme.json`/token mapping. Those are material contract surfaces. Editor interface locale and website translation locale should remain distinct in any added translation policy.

The cited schema-generation commands and four current constants match the repository. BWB-041, BWB-043, and BWB-075 exist in the local roadmap with the stated broad roles.
